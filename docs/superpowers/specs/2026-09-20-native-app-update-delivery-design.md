# 错题智库：标准 Windows 应用与安全更新设计

## 目标

让“错题智库”在用户心智和 Windows 行为上都成为真正的桌面应用：首次安装后，用户只从桌面、开始菜单或任务栏启动；后续版本由应用内检查、下载并安装，不再要求用户每次寻找安装包。

安装包仍然保留，但它只承担首次安装、修复安装和离线升级，不再作为日常启动入口。

## 当前问题

- 当前主程序已经是 Tauri 原生 Windows 应用，包含 `cuoti-zhiku.exe`、`WebView2Loader.dll` 与卸载器，并已有桌面和开始菜单快捷方式。
- 现有快捷方式指向 `C:\Users\whz21\Desktop\错题智库\cuoti-zhiku.exe`。应用文件夹直接暴露在桌面上，容易让用户把安装包、程序文件和快捷方式混为一谈。
- 应用没有更新器，因此新版本只能重新下载安装包。
- 用户数据位于应用数据目录，不应跟随程序目录迁移或卸载而丢失。

## 方案比较

### A. 标准安装 + 应用内安全更新（采用）

应用安装到当前用户的标准程序目录，桌面只留下一个快捷方式。设置中提供“关于与更新”，后台只做低打扰检查；发现新版本后由用户确认，应用下载经过签名验证的更新并重启安装。

优点是最符合普通用户预期，保留卸载、快捷方式、版本管理与安全验证。代价是发布流程必须保管更新私钥，并生成配套更新元数据。

### B. 绿色便携版

把程序和依赖打成压缩包，用户解压后直接运行。它减少首次安装步骤，但仍需要保留整个文件夹，无法可靠创建卸载入口、自动更新与文件关联，移动或误删 DLL 还会导致无法启动。因此不作为主要交付方式。

### C. Microsoft Store / MSIX

商店负责安装与更新，用户体验最统一，但需要开发者账户、商店审核和 Windows 代码签名准备。它适合作为公开推广的后续渠道，不阻塞当前版本。

## 安装与启动模型

1. 0.5.2 作为一次迁移版本，使用 Tauri `currentUser` 安装模式进入 `%LOCALAPPDATA%` 下的标准用户程序目录，不要求管理员权限。
2. 桌面与开始菜单快捷方式只指向该目录下的 `cuoti-zhiku.exe`，名称统一为“错题智库”。
3. 首次成功启动后检查旧的桌面程序目录，但不会自行删除。只有确认新程序、用户数据库和原件目录均可读取后，才在界面提示“旧程序文件可以清理”；任何清理都必须由用户明确确认。
4. 用户的 SQLite、原件、备份偏好和 API Key 继续位于应用数据或系统凭据存储中，不搬进程序目录。
5. 安装包文件可以由用户删除；删除安装包不会影响已经安装的应用。

## 应用内更新体验

“偏好设置 → 关于与更新”显示：

- 当前版本；
- 最近一次检查时间；
- “检查更新”按钮；
- 有新版本时显示版本号、简短更新说明和“下载并安装”；
- 下载时显示确定进度，安装前明确提示应用会关闭并重新打开；
- 最新版本时只显示克制的“已是最新版本”，不弹全屏成功提示。

应用启动 15 秒后可进行一次非阻塞检查，最多每 24 小时一次。网络不可用、GitHub 不可达或没有更新时不打断学习；仅在设置页显示可重试状态。应用永不在用户答题、编辑或 AI 建议保存过程中强制重启。

## 安全更新链路

采用 Tauri 2 官方 updater 插件与 GitHub Releases 静态更新元数据：

- `tauri.conf.json` 固定内置更新公钥与 HTTPS `latest.json` 地址；
- 每个 Windows 更新产物同时生成 updater 签名；
- 更新私钥只离线保存并写入 GitHub Actions Secret，绝不提交仓库、日志或安装包；
- 客户端必须先通过 Tauri 签名校验，再允许安装；签名缺失、错误、版本格式非法或 URL 非 HTTPS 时失败关闭；
- 不通过 shell 下载并执行任意 exe，不允许跳过签名校验；
- Windows 商业代码签名与 Tauri 更新签名是两层不同保障：本阶段先完成不可关闭的更新签名，商业代码签名作为后续发行增强。

官方依据：[Tauri Updater](https://v2.tauri.app/plugin/updater/)、[Windows Code Signing](https://v2.tauri.app/distribute/sign/windows/)。

## 发布流水线

新增仅由语义版本标签触发的 Windows 发布工作流：

1. 校验 `package.json`、`Cargo.toml`、`Cargo.lock` 与 `tauri.conf.json` 版本一致；
2. 执行 lint、TypeScript、前端测试、Rust 测试和生产构建；
3. 使用 GitHub Secret 中的 Tauri 更新私钥构建 NSIS 与 updater 签名；
4. 生成 `latest.json`，其中版本、下载 URL 与签名必须对应同一最终产物；
5. 将安装包、签名、`latest.json`、SHA-256 和发布说明上传到同一个 GitHub Release；
6. 下载已发布产物重新计算哈希，并执行安装、启动与更新冒烟验证后才将 Release 标为正式。

首个带更新器的版本必须通过安装包手动安装一次。此后版本才可在应用内更新，这是建立公钥信任根所必需的一次迁移。

## 组件边界

- `UpdateService`：只封装检查、下载、安装和进度事件，不包含界面状态。
- `UpdatePanel`：负责版本、状态、进度、错误与用户确认。
- `UpdateCheckStore`：只保存最后检查时间与暂缓的版本号，不保存私钥或下载内容。
- 发布工作流：只在受保护标签发布，私钥只通过 Secret 注入构建进程。

这些单元使用窄接口，便于在测试中替换更新服务，避免真实下载或真实重启。

## 错误处理

- 离线或 GitHub 超时：保持当前版本可用，显示“暂时无法检查”，允许手动重试。
- 签名或元数据失败：禁止安装，显示安全错误，不提供绕过按钮。
- 下载中断：丢弃不完整产物，当前安装不受影响。
- 安装启动失败：保留当前运行版本与用户数据，提供 GitHub Release 手动下载链接作为恢复路径。
- 正在编辑：更新可以下载，但安装操作需要用户确认，并在保存完成后执行。

## 测试与验收

- 单元测试覆盖无更新、有更新、离线、签名错误、下载中断、重复检查节流和编辑中禁止重启。
- 组件测试覆盖键盘操作、焦点恢复、进度状态、错误重试和减少动态效果。
- 发布测试覆盖版本一致性、`latest.json`、签名文件、最终安装包哈希和无密钥泄漏。
- Windows 实机测试覆盖：从 0.5.1 手动安装迁移版本、快捷方式启动、应用内更新到下一测试版本、更新后数据与原件仍可读取。
- 回滚路径是保留上一版正式安装包；更新失败不修改数据库结构或删除用户资料。

## 非目标

- 本轮不实现 Microsoft Store 发布。
- 本轮不购买或伪造 Windows 商业代码签名证书。
- 不做静默强制更新，不在后台自动重启。
- 不把用户题目、教材、API Key 或使用数据发送到更新服务。
